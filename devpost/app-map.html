このアプリは何か

指でドローンを動かして街の物を吸収し、指を止めて周囲を吸い込み、押したまま素早く円を描くとハイパーが成立、離すとカラーボールを放ってターゲットを削る。5分で一区切り、進行は端末のlocalStorageに保存され、Service Workerで通信なし起動もできる。

主要な部品
  • src/config.js — 数値の正本（制限時間・半径・ダメージ・HPなど）
  • src/game.js — ルール。移動・吸収・放出・ダメージ・時間
  • src/input.js — 指の「移動 / 静止 / 急回転」判定
  • src/render.js — Three.js の描画と演出
  • src/main.js — 入力・状態・描画・HUD・保存の配線
  • src/persistence.js — 保存・復元とデータ検証

1つの行動が、どこを通って画面に出るか

参照ルート（3か所）未ツアー・参照用

このルートは学習ツアーとして一緒に歩いた記録ではなく、コードから作った参照用の道順です。

  1. 入力の判定 — src/input.js の detectHyper(points)。 ROTATION_WINDOW_MS = 900 の窓の中で、丸さ（偏差30%以内）・合計角度（1.8π以上）・一方向性（85%以上）を見る。 GestureInput#update() が 350ms の静止を charging に変え、そこから円のサンプルを集める。
  2. 配線 — src/main.js の new GestureInput(canvas, { onRelease(hyper) { ... } })。 離した瞬間に release(state, hyper) を呼び、persist() で保存する。
  3. ルールと結果 — src/game.js の release(s, hyper) → damage(s, amount)。 与ダメージは energy × baseDamage × (hyper ? hyperMultiplier : 1)。数値は src/config.js の CONFIG に集約。

ここを変えたい、と思ったら

  • ハイパーが成立しにくい / しやすい → src/input.js の ROTATION_WINDOW_MS、detectHyper 内の 1.8（必要角度）と 0.3（丸さの許容）。
  • ゲームの難易度・テンポ → src/config.js の limitSeconds・targetHp・energyCap・baseDamage・hyperMultiplier。
  • 吸収の手触り → src/game.js の moveDrone() 内 passRadius 判定と collect()、吸引半径は step() の suctionRadius。
  • 見た目・演出 → src/render.js の GameRenderer（update() が状態を受け取る）。
  • HUDの表示文言 → index.html の要素と src/main.js の $('mode').textContent = ... 付近。
  • 保存のタイミング → src/main.js の frame() 内 now - lastSave >= 1000。

再利用できる型（この作品で実際に起きたこと）

型: 「端から端まで動く状態」を保ったまま、目標に届くまで判定を調整する。

円運動の判定は、数学的には正しい点列で成立しても、実ブラウザでは複数の指位置が1つのイベントにまとめられて届くため取りこぼした。 そこで getCoalescedEvents() を時刻順に読む修正が入り、回帰テスト tests/input.test.mjs の quick circles qualify clockwise and counterclockwise… と circle during charge locks hyper once and never changes movement direction が守っている。

さらに実プレイの録画では、円が900ms の窓に収まらない速度だと成立しないことが実測で分かった（同じ図形でも遅いと不成立）。 つまり「テストが通る」と「実際に気持ちよく決まる」は別で、E2Eで動かして初めて分かる条件が残る。

別の作品でも同じやり方が使える: 判定ロジックは単体テストで固め、実入力の粒度（まとめ・遅延・端末差）だけを実機・実ブラウザで確かめる。範囲を広げずに品質を上げたいときは、この「単体で固める層」と「実入力で確かめる層」を分けて持つ。
